Update (§16 robustness check): every amber chip above was widened to all 3 swallow-types and both regimes (cross-session was never tested for any of them before). The headline result: cross-session generalization is where every one of these approaches breaks down — ratios, phase, and TRF all show nominal within-session promise on middle/pooled (later mostly overturned by a bootstrap-CI audit, see below) that vanishes or reverses almost universally in cross-session. K-means clustering variants are the one exception where the original "doesn't help" verdict holds cleanly at full scope. A real bug was also found and fixed along the way: spatial_moments crashed when combined with ratios/phase (negative pseudo-band values broke its power-weighted spread math) — now an explicit guard instead of a silent mid-sweep crash. Full tables: §16 of the technical dashboard.
Follow-up: regularization wasn't tuned for the wider band axis. Ratios/phase expand the band axis from 4 to 6–10 pseudo-bands, but the fixed-ridge decoder's regularization strength (α=3000) was only ever validated at the original 4-band width — exactly the situation fixed regularization isn't safe for. Both sweep scripts now auto-substitute ridge_cv (tuned α per fold) whenever ratios or phase features are on, and the sweeps were re-run. Against the corrected baseline (2026-07-23), this recovers almost nothing within-session either — only 6 of 36 ratios+phase cells even nominally beat the corrected baseline (down from a nominal "roughly double" against the stale one), and just 1 of those 6 survives a bootstrap-CI check. Cross-session was, separately, already known to be unaffected by the fix. A separate check also ruled out session-specific hardware artifacts as the cause of the cross-session collapse (band-power features turned out to be more session-separable than ratio/phase features, the opposite of that hypothesis). Net: the cross-session collapse for these two feature types is not a fixable regularization or hardware-artifact issue — it remains unexplained and open.
GLOSSARY

Terms, disambiguated

The three amber-bordered entries below are the ones most likely to get confused with each other — they all involve the word "pooled" or "joint" but control completely different, independent things.

joint (cleaning)
The ICA+Kalman denoising matrix is fit once, on both sessions' data pooled together, instead of separately per session. A preprocessing choice — happens before any feature or decoder work. Opposite: independent cleaning.
Confusable with "pooled" below — different axis entirely
cross-session (regime)
Each leave-one-event-out training fold uses events from both sessions combined, not just the session the held-out event came from. A decoder training/evaluation choice — happens after cleaning and feature engineering are already done. Opposite: within-session.
Confusable with "joint" above and "pooled" below
pooled (swallow-type)
Final-swallow and middle-swallow events are merged into one undifferentiated event class — the decoder never knows or distinguishes which subtype an event was. Not a post-hoc split of results by subtype; the merge happens before training. Alternatives: final only, middle only.
Confusable with "cross-session" above — this is about event LABELS, that's about TRAINING DATA
within-session (regime)
Each session gets its own, completely independent, leave-one-event-out train/test cycle. Session A never sees session B's events during training, and vice versa. This is the regime used for every heatmap in §4 and every extended-exploration result (§9–§13).
LOEO (leave-one-event-out)
The cross-validation scheme: for every real swallow event, train on every other event (within the regime's scope — one session or both) and test on the held-out one. Repeated once per event, scores averaged.
fixed-config sweep
Every (window_s, lead_s) combination is run explicitly, with the SAME config held fixed across every fold in that run — as opposed to an earlier, abandoned approach where an inner search picked a possibly-different config per fold (which doesn't correspond to any single deployable decoder).
window_s / lead_s
window_s: how many seconds of data the decoder's feature window spans. lead_s: how far before the target instant that window ends (0 = ends right at the instant). See the timeline schematic below — words alone undersell this one.
causal / acausal
Causal (lead_s ≥ 0): the feature window only ever looks at data from before the instant being scored — a real-time-deployable predictor. Acausal (lead_s < 0, tested deliberately in one follow-up, §10): the window looks after the instant — describes detecting an already-started event from its aftermath, not predicting one. Never used for the core grid.
boxcar
The default feature representation: every value inside the causal window is averaged down to one number per channel×band. Used for every core-grid result.
lagged / TRF
An alternative representation (temporal-response-function style): instead of averaging, every individual lag inside the window keeps its own column. Tested head-to-head against boxcar on 2–3 feature methods (§9/§10/§13) — boxcar won almost every comparison.
k-optimized / window-specific / combined
Three variants on k-means channel clustering (§11): k-optimized picks the cluster count via a silhouette score instead of a fixed default; window-specific restricts the clustering INPUT to the same time-window the decoder's feature window uses (instead of the channel's whole-session behavior); combined is both at once.
decoder architectures
ridge (linear, L2-regularized — the strongest performer throughout), ridge_cv (ridge with a tuned regularization strength instead of one fixed value), hmm (generative 2-state model — weakest on average, but one sharp exception, see the dashboard's §3), logreg/lda (linear classifiers), lstm (recurrent neural net), gbt (gradient-boosted trees — weakest overall, but the only decoder where lagged beats boxcar).
onset-F1 @ [tolerance]
A predicted onset "counts" as correct if it falls within the stated tolerance (e.g. 500ms) of a real onset. F1 = harmonic mean of precision and recall on that matching. The primary number throughout is 500ms tolerance.
category 1 / category 2 (feature methods)
Category 1: methods that never use real electrode position (identity, pca, kmeans clusters, csp). Category 2: methods built directly from bank/row geometry (zones, zones-bank-only, zones+contrast, spatial moments).

Channel groupings, on the real electrode array

The three most-referenced category-2 (geometry-aware) groupings, drawn on this dataset's actual 72-channel array layout — corrected geometry (see callout below), oriented so the wire bundle/medial side is to the right and anterior is up, matching the physical channel map. Every dot's color is which group it lands in.

identity vs. zones (bank × row) vs. zones (bank only)

Bank = lateral/middle/medial third of the array (C/B/A) — approximately: two columns physically straddle a bank boundary (visible above as split-color columns), not a clean three-way split, since bank wiring on this array isn't column-aligned everywhere; row = top/middle/bottom third (R1/R2/R3, dashed lines at the group BOUNDARIES in the middle panel — always an equal split by construction, independent of the bank straddling). "zones (bank×row)" intersects both for up to 9 groups; "zones (bank only)" ignores row entirely for 3 groups. Anterior/posterior and medial/lateral axis labels added directly to each panel.

Geometry correction, 2026-07-21: the probe file this pipeline had been reading (probe_utah_96ch.json) turned out to be a placeholder — a simple synthetic geometric sweep, not the array's real (scrambled, connector-pinout-driven) channel-to-position map. Checked against a physical channel map: the old file matched the real layout on essentially 0 of 96 channels under every possible flip/rotation. It's now been replaced with positions built directly from the real map and verified to match all 96 channels exactly.

What this did and didn't affect: bank labels (A/B/C) come from the channel NAME string, never from position, so they were always correct — zones (bank only) and any bank-name-grouped result stand as reported. What used raw (x,y) directly — row assignment, zones (bank×row)'s row component, zones+contrast, spatial_moments, spatial smoothing, and any array-layout topomap/heatmap — used the wrong geometry and needs re-verification. A direct before/after check on this dataset's spatiotemporal topomap already shows a real, visible difference (a low-gamma spatial pattern that flips which side of the array it's concentrated on) — not a subtle effect.
Not shown here, worth knowing about: kmeans clusters and pca group channels by their STATISTICAL behavior instead of physical position — a channel's group membership can (and often does) cut across bank/row boundaries entirely, and this was never affected by the geometry bug (neither method ever consumes position). §11 of the technical dashboard shows this directly: the k-means clustering's winning grouping visibly mixes all 3 banks within a single cluster.

Of 8 "beats baseline" cells checked across every axis on this page, only 1 survives — i.e. has the core-grid baseline fall outside its 95% CI. The rest have the baseline comfortably inside the interval: not statistically distinguishable from sampling noise at these event counts (16–56 events per cell). Cells marked ✓ survive; cells marked n.s. (muted fill) do not. Negative-delta ("hurts") cells were not re-tested — they already support the "this doesn't help" conclusion, no rescue needed.
